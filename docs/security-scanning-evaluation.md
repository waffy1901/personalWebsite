## Rollout and verification

**Phase 1.** Waffy owns triage. Run Gitleaks locally when staging credential-adjacent or CI configuration changes and before pushing those commits. Verify the version and release digest, use the default rules, and review any redacted output locally. The staged check uses `gitleaks git --pre-commit --staged --redact=100 --no-banner --max-target-megabytes=2 --timeout=30 .`. For committed changes, replace `--pre-commit --staged` with `--log-opts='<reviewed-base-sha>..HEAD'`. Check that the intended inputs were scanned. Keep the check advisory. Review rule noise and binary updates quarterly. Phase 1 adds **0 Actions minutes and $0 recurring spend**, and requires only local checkout access. Use CodeQL, npm audit and workflow lint on the existing PR triggers and the native scheduled/default-branch controls for new disclosures. [Standard public runner billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)

**Optional Phase 2.** Evaluate the CodeQL Python default suite locally against deployment and reporting code. Keep pilot SARIF local because uploads under CodeQL can affect the existing tool rule. Waffy can scope a trusted manual or weekly lane once a pilot demonstrates incremental signal and confirms how uploads affect the ruleset. Estimate 2-5 Linux runner-minutes per run including setup, or 8-25 per month at weekly cadence. For a demonstrated runtime gap, try a manual ZAP passive baseline on a locally served production build. Seed the needed routes, cap the spider at one minute and the run at five, and restrict traffic to the local target with passive checks and no form submissions. Scope any follow-up issue to the confirmed gap and its verification. These pilots support manual local use. [CI hardening #168](https://github.com/waffy1901/personalWebsite/issues/168), [CodeQL #286](https://github.com/waffy1901/personalWebsite/issues/286), [pinning #308](https://github.com/waffy1901/personalWebsite/issues/308)

**Trust boundary for a future CI pilot.** First-time public fork contributors currently need approval to run workflows. For a static fork check, use `pull_request`, an ephemeral GitHub-hosted runner, `contents: read`, checkout without persisted credentials, and pinned binaries or actions. Read reviewed rules from the base, treat fork files as data, and cap scope and time. Keep code execution and secrets out of that job. Vendor CLI tokens belong in trusted jobs. GitHub App integrations use their own approved access. The existing `pull_request_target` job is metadata-only. Keep raw findings out of logs, annotations, PR comments, artifacts and caches. If trusted main-branch reporting needs GitHub code scanning, confirm report visibility and use a dedicated SARIF category and job-level `security-events: write` for approved non-secret results. GitHub's upload exception for `pull_request` runs applies to code scanning. Budget for the 10 MB compressed SARIF limit, GitHub's 1,000 REST requests/hour/repo per Actions token, and upstream download throttling. [Fork approval](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/approve-runs-from-forks), [fork security](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target), [SARIF uploads](https://docs.github.com/en/code-security/how-tos/find-and-fix-code-vulnerabilities/integrate-with-existing-tools/upload-sarif-file), [fork SARIF permissions](https://docs.github.com/en/code-security/reference/code-scanning/troubleshoot-analysis-errors/resource-not-accessible), [SARIF limits](https://docs.github.com/en/code-security/reference/code-scanning/sarif-files/sarif-support), [API limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)

**Private triage and reporting.** Confirm exposure and reachability before assigning severity. Revoke or rotate a live credential immediately. Proposed fix or mitigation targets are one day for critical, seven days for high, 30 days for moderate, and 90 days for low. Review advisory jobs for confirmed new findings, duplicates, failures and wall time before proposing any new blocking rule. Consider blocking only on confirmed high or critical signal with an owner and measured false-positive rate. Record false positives and temporary exceptions privately by exact rule and scope, with a reason, owner and expiry of at most 30 days. Rerun on the fixed SHA with recorded tool, rule and database versions and verify the native alert disposition where applicable. Interpret a clean scan within its recorded input, rule and data coverage.

For the Engineering report, use counts by source, severity and category, confirmed fixes separate from dismissals, and time from detection to verified fix with sample size. Deduplicate advisory aliases and repeated findings within each source. Distinguish unavailable sources from measured zeros. The hosted collection passed with Dependabot excluded. Use the local collector with read access for that source. Retain detailed findings, fingerprints and evidence privately.
